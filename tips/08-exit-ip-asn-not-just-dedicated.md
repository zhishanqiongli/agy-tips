# 08 · 换了独享 IP 怎么还报错？Google 查的是 ASN 归属，别被机房骗了

> **“我都特地花钱买了一台独立的海外 VPS，IP 也是独占的，凭什么跑两步还是报 `User location is not supported`？”**

在 [Tip 06](06-dedicated-exit-ip.md) 中，我们搞定了用自建 SSH SOCKS5 隧道为 `agy` 搭建专用出口。但在实际跑了几天之后，我们遭遇了一个极其玄学的新问题：

> 换上独占海外 VPS 之后，地区不支持的报错确实断崖式下跌，**但它没有彻底归零**。每跑三五十次，还是会抽风冒出来一两次，直接把正在跑的自动化任务掐断！

---

## 侦探式排查：抓包看 IP背后的“族谱”

在终端里走这条代理隧道去查 IP 归属：

```bash
curl -s --socks5-hostname 127.0.0.1:7899 https://ipinfo.io
```

返回的信息乍一看没毛病：国家代码是 `US`，城市是硅谷（Silicon Valley），机房物理坐标清清楚楚在美国。

**但视线往下移一行，看到 ASN（自治系统编号）一栏时，真相大白了：**

> 这个 IP 段背后的注册主体和广播机构，赫然写着国内某云厂商的海外分支机构！

这下终于摸清了 Google 风控的深层逻辑：
* **很多国内大厂出海的海外机房 IP**，虽然物理位置在美国，但其 IP 地址块在 BGP 路由广播与 WHOIS 注册机构库（ASN）里依然打着强烈的母公司烙印。
* Google 内部的风控规则库极其严格，它判定你的请求到底来自哪里，**看的是“地理位置库 + ASN 注册主体库”的交叉校验**！
* 当两套数据库打架时（地理库说在美国，ASN 库说跟受限地区大厂关联），Google 的策略就是间歇性抽风拒掉你的请求。

---

## 尝试过的另一个天坑：套 Cloudflare WARP？

当时我们想：“既然是国内厂商 ASN 的锅，那换成西方纯正大厂的 ASN 总行了吧？”

于是我们在 VPS 上套了一层 Cloudflare WARP（`warp-cli` 代理模式），ASN 变成了响当当的 `AS13335 (Cloudflare)`。

**结果当场翻车，情况反而更恶劣了！**  
同样的测试脚本，被 Google 拒绝的比例比之前还要高一倍。

> **教训**：千万别拿知名公共 VPN / WARP 当银弹。Google 对 WARP 这类公共出口网段有极高敏感度的专门风控，不仅不会更稳，反而直接撞枪口上。

---

## 终极退烧方案：用目标大厂自家的 VPS 做跳板

既然要调用 Google 的 API，最稳妥、最干净、最有排面的出口，**就是 Google 自家的机房 IP（Google Cloud / GCP）**！

用同一套 [Tip 06](06-dedicated-exit-ip.md) 的隧道架构，只需要把远端服务器换成 GCP 的机器：
1. **区域选择**：选择离 API 服务器就近的美区（比如 `us-west1` 或 `us-central1`）。
2. **机型选择**：开一台最基础的 `e2-micro` 就足够当代理跳板了，完全不需要高配置。
3. **⚠️ 警惕账单陷阱**：很多人看博客说“GCP e2-micro 永久免费”，但请注意：**从 2024 年开始，GCP 对任何外网固定 IPv4 都要收费（约 $3.65/月）**，免费额度只免机器算力，不免外网 IP！综合算下来一个月大约 4~5 美元（人民币三十块钱左右），为了稳定的全自动开发环境，这笔投资绝对值。

换上 GCP 机器后，我们用自动化脚本循环跑了几百次探活与代码生成，**地区错误彻底清零，再也没有抽风过哪怕一次**！

## 配套工程改进

为了适配多云与私钥管理，仓库里的脚本已做如下优化：
* [`scripts/agy-tunnel`](../scripts/agy-tunnel)：支持了 `AGY_TUNNEL_IDENTITY` 环境变量，允许指定 GCP 专用的 SSH 私钥文件，不强行依赖默认的 `id_rsa`。
* [`scripts/agy-do`](../scripts/agy-do)：内置了**失败自动重试机制**。一旦探测到日志中偶发地区判定错误，只要当前没有产生半成品代码（工作区干净），脚本会自动退避 30s/60s 并原地重试最多 3 次，保证无人值守时不被偶发抖动打断。
