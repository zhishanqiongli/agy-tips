# 05 · 「施工模式」最佳实践：Claude 出脑力写卡，agy 出劳力搬砖

> **核心矛盾**：Claude Code 极其聪明，架构把控一流，但直接让它吭哧吭哧写具体业务实现是真正的 **Token 吞噬兽**，一个中等规模的功能几万 Token 就没了，钱包顶不住。  
> 另一边，`agy` 走 OAuth 走的是 Google AI Pro / Ultra 的**包月订阅**，在额度内写代码基本相当于“零边际成本”。

聪明的工程师不当单打独斗的英雄，我们让它们**混合双打**：

---

## 角色分工：总包与分包的极致分工

| 角色 | 扮演身份 | 核心职责 |
| :--- | :--- | :--- |
| **Claude Code** | **总工 / 老司机** | 负责拆解架构、编写精密任务卡、审查 Diff、运行自动化验收、写返工清单。只在最棘手的小逻辑和架构上亲自下场。 |
| **agy** | **施工队 / 砖头工** | 严格按照任务卡执行代码修改、跑单测自检、独立生成 Commit。绝不多想，按图施工。 |

启动施工的现成脚本位于 [`scripts/agy-do`](../scripts/agy-do)，用法极其爽快：
```bash
agy-do <任务卡.md> [--async] [--here]
```

---

## 刚跑起来时踩过的两大血泪教训

**说实话，最开始跑不顺，问题根本不在 agy 偷懒，而是“老司机”太没规矩了！**

### 1. 司机根本不派活，老想自己上
只要「施工模式」只是嘴上说说，Claude 潜意识里默认还是自己动手写代码。一旦给它开了“复杂逻辑自己写”的口子，它恨不得把整个项目都揽过来。
> **治法**：在 Claude 端做成**显式技能（Slash Command / Skill）**，强制必须走命令触发，绝不指望 AI 的自律。

### 2. 卡写得太薄 → agy 疯狂糊弄 → 验收还查不出来
任务卡写得语焉不详（比如“把某模块重构一下”），agy 就会开始天马行空的自由发挥。更坑的是，Claude 验收时如果只看 agy 结尾写的那段“自我吹捧总结”，百分之百被糊弄过去。
> **治法**：设立两道铁闸——**发卡前的质量闸门**与**验收时的机器硬核判定**。

---

## 闸门一：发卡前检查清单（任何一条不符直接打回）

1. **改动文件清单**：必须是**精准的绝对/相对文件路径**，严禁出现“相关文件”、“视情况调整”等模糊字眼。
2. **怎么验收**：每一条都必须是**可以直接复制到终端执行的命令 + 明确的期望输出**。任何“确认功能正常”、“界面美观”等不可执行的废话一律禁止。
3. **前置假设自己先 grep 验一遍**：卡里只要写了“现在的逻辑是 X”、“这个函数只被 Y 调用”，司机必须自己先 grep 确认过。你敢写错，agy 就敢照着错的代码一路狂奔。
4. **先跑一次验收命令记下基线**：在代码还没改动前跑一遍。没有基线，你怎么知道改完之后测试通过是代码修好了，还是原来就一直通过的假象？
5. **通读自问**：这份说明书，一个对这项目完全陌生的外包程序员能不能丝毫不问问题照着干完？如果不能，这就是一张烂卡。

---

## 闸门二：机器自动化验收（先跑脚本，再人肉审 Diff）

设定 `RANGE = <base>...HEAD`（Worktree 隔离模式）：

| 检查项 | 验证手段 | 判定标准 |
| :--- | :--- | :--- |
| **有没有施工回执** | `grep -A20 '## agy 回执' <任务卡.md>` | 没填回执说明施工未闭环 |
| **改动越界没有** | `git diff --name-only $RANGE` 与卡片白名单对比 | 改了白名单之外的文件直接报警 |
| **混入临时文档没有** | 检查 diff 里是否带了 progress/plan/notes | 临时文档不得混入提交 |
| **断言归零是否改名糊弄** | `git diff $RANGE \| grep -E '^[-+].*<符号名>'` | 只有 `-` 算真删除，出现换名重新声明视为欺骗 |
| **卡片验收命令执行** | 在 Worktree 环境完整跑一遍 | 输出必须与期望基线完全对齐 |

**人肉看 Diff 的三处死角**：
1. 卡片里给的前提条件，它有没有自己二次确认？
2. 有没有偷工减料？（写了个空函数、留了 `// TODO`、用 `catch {}` 吞了异常、把单测断言改宽松而不是把逻辑改对）。
3. 有没有手痒改了无关代码的格式。

> [!WARNING]
> **铁律：返工最多两轮！**  
> 如果第二轮返工还没改好，别喂第三轮了——要么是任务卡本身设计有漏洞，要么是这个问题已经超出了当前模型的能力边界。司机果断接手自己写，反复拉扯消耗的 Token 比自己写贵得多。

## 进阶技巧：异步无人值守施工

前台模式下跑 `agy-do`，Claude 经常要干等二十分钟，会话完全被阻塞。

加上 `--async` 参数，把施工丢进后台独立执行，日志落盘在 `~/.agy-runs/<项目名>--<slug>/out.log`。**当脚本完成时，由外层 Shell 负责落一个 `exit` 文件（写入进程退出码），作为绝对可信的完成标志**。

在司机端挂一个轻量的看门狗等待唤醒即可：

```bash
until [ -f ~/.agy-runs/<项目名>--<slug>/exit ]; do sleep 20; done
echo "施工完成，退出码 rc=$(cat ~/.agy-runs/<项目名>--<slug>/exit)"
```

### 为什么盯文件比盯日志高级？
* **原子性**：文件要么存在要么不存在，绝不会因为读到写了一半的日志文本产生误判。
* **外层把关**：不管是正常收工、抛出异常还是超时被系统掐断，外层 Shell 必定会落盘带有退出码的 `exit` 文件。即使 agy 内部崩溃，司机也不会无限傻等。

配合 [`scripts/agy-runs`](../scripts/agy-runs)，随时一览所有后台任务状态（运行中、待验收、异常退出）。

## 🛠️ 四个踩大坑踩出来的工程细节

1. **Worktree 隔离与防逃逸**：agy 曾有把 Worktree 里的 `.git` 软链解析回主仓、顺手把提交打到主分支的前科。脚本在施工前后会对主分支 HEAD 拍快照，一旦发现越界立即报警！（但不要自动回滚，因为可能有别的并发任务在推进主分支）。
2. **起跑前静默信任 Worktree**：如 [Tip 04](04-worktree-untrusted-folder-print-timeout.md) 所述，新建的 Worktree 绝对路径并不在信任白名单内，必须在调用 `agy -p` 前静默写入配置，否则秒超时。
3. **保留 `--here` 原地施工通道**：对于 Tauri、Xcode、或者有几百兆 `node_modules` 的庞大工程，新建 Worktree 重新下依赖全量编译的耗时太惊人。`--here` 允许在当前目录就地改，但前置检查要求工作区必须 100% 干净。
4. **命令行传参顺序**：记住 `--print-timeout` 必须放在 `-p` 参数前面，否则 `-p` 会误把后面的超时参数当成 Prompt 字符串吃进去。

## 提交署名：分清谁该对代码负责

脚本内部统一注入环境标记：
```bash
GIT_AUTHOR_NAME=agy GIT_AUTHOR_EMAIL=agy@antigravity
```
这样在后续审查与回顾时，敲一句 `git log --author=agy`，所有由 AI 施工队搬砖写出的提交一清二楚，责任划分明明白白。
