# 14 · 隧道没断但 agy 慢如蜗牛？单条 SSH 队头阻塞排查与多路复用

> **“最折磨人的故障从来不是‘直接断网’，而是所有指示灯全绿，但它就是慢得像上个世纪的拨号上网！”**

在 [Tip 13](13-tunnel-restart-gap-and-ssh22-blackhole.md) 中，我们解决了隧道断开导致的崩溃。而这篇要聊的，是更让人挠头的另一半问题：
**隧道自始至终全是通的**，`agy-tunnel status` 绿油油一片，健康检查次次秒过，但终端里的 `agy` 却慢得离谱——敲一句话回车，要足足干等半分钟才能挤出一个字。

翻遍网络抓包也看不出任何异常，因为物理网络真的没断。那时间到底被谁偷走了？

---

## 侦探出动：剥离业务，测量纯净往返延迟

为了排除模型生成慢的干扰，我们直接用 `curl` 测试一个极小的纯 IP 响应接口（`api.ipify.org`，只返回一行 IP，排除了带宽吞吐干扰，测的就是纯净的网络 RTT 往返耗时）：

```bash
$ curl -x socks5h://127.0.0.1:7899 -o /dev/null -w "%{time_total}\n" https://api.ipify.org
26.44 秒          <-- 前置代理入口（慢得怀疑人生！）
$ curl -x socks5h://127.0.0.1:7896 ...   8.89 秒  <-- 节点 A
$ curl -x socks5h://127.0.0.1:7895 ...   超时      <-- 节点 B
$ curl -x socks5h://127.0.0.1:7897 ...   1.20 秒  <-- 本地普通代理作为基线
```

但诡异的是：登录进那台海外 VPS 查看，`load average: 0.08`，CPU 闲得发慌，本地直接 ping 服务器延迟 240ms，丢包率 0%。新开一个临时 SSH 窗口测同一个端口，往返稳定在 1.1 秒。

## 致命元凶 1：一条 `ssh -D` 就是一条单道马路，大请求堵死所有人

`ssh -N -D` 在底层本质上只是**单一的一条 TCP 长连接**。它把所有客户端并发的 HTTP/HTTPS 请求全部打包复用进这一根管道里。

这意味着：**只要这根管道里突然出现了一个大文件传输，后面排队的所有小请求全部被活活堵死——经典的 TCP 队头阻塞（Head-of-line Blocking）！**

翻看 gost 的底层转发流量日志，抓到了铁证：
```text
"host":"play.googleapis.com:443","inputBytes":203805334,"duration":2406228611417
"host":"daily-cloudcode-pa.googleapis.com:443","inputBytes":16977798, ...
```

一条 203MB、两条 16MB！这些是 `agy` 下载上下文缓存、拉取模型大响应或插件时的正常流量。但在它们占满这条长连接的几十分钟内，你在终端敲的每一句交互短请求，都只能跟在 200MB 的屁股后面寸步难行，响应时间直接被无情拖到 20 秒以上！

> [!WARNING]
> **排查时最大的幻觉**：  
> 当你发现慢、停下任务准备排查时，那个大文件往往刚好下完了！此时你去测试，隧道立刻恢复为秒级的 1.0 秒。很多人第一轮就被骗了，以为是“长连接被运营商限速”，甚至折腾起定时重连。  
> **真正法则**：测量前务必确认后台没有任何任务在跑（静默期测量才是真实物理延迟）。

**极简解法**：上游从 1 条 SSH 扩容到 3 条独立 SSH，由本地前置调度器把并发流量自动分摊，小请求再也不会被大车堵死在单行道上。

## 致命元凶 2：22 端口平时的路径质量本身就差

在 [Tip 13](13-tunnel-restart-gap-and-ssh22-blackhole.md) 中我们提过用 22 和 443 端口互备。但当时我们图省事，把 22 和 443 放在同一个负载均衡池里轮询。

这次静默期逐个端口精密测试，真相触目惊心：

| 上游端口 | 静默期实测往返耗时（4 次采样） |
| :--- | :--- |
| **443 端口** | 1.01s / 1.03s / 1.02s / 1.30s（极其稳定） |
| **22 端口** | 16.32s / 3.10s / 1.56s / 10.73s（疯狂抖动） |

在无负载状态下，22 端口的物理延迟本身就比伪装成 HTTPS 的 443 端口烂得多！所谓的“双腿走路”，本质上是**一条健步如飞的好腿绑着一条瘸腿**，每次轮询到瘸腿，终端体验就瞬间卡顿。

**架构优化**：日常流量 100% 走 443 端口池；22 端口降级为纯应急备份——只有当三条 443 线路**全部死亡**时，才切到 22 端口苟命，并在 2 小时后自动切回 443。

## 致命元凶 3：健康检查只测“活不活”，不管“快不快”

原先的健康检查脚本设置了 25 秒超时，只要 25 秒内通了就标为绿灯。上面那些耗时 16 秒的半死状态，在它眼里全算“健康”！

**优化原则**：在乎性能，探针就必须测性能。
* 把探活判定收紧为：**必须通且耗时 < 8 秒才算健康**（正常线路是 1 秒左右，8 秒留足了余量）。
* ⚠️ **但千万带上前提条件**：这个 8 秒阈值**只在没有任何 `agy` 实例在跑时**生效！如果此时检测到有任务正在跑，自动放宽回 25 秒，避免把正在传输大文件的正常连接误杀。
* 依然坚持 **连续 3 次超时才 kill** 的防抖铁律。

## 终极网络架构拓扑

```text
agy 进程
   ↓ (本地 SOCKS5)
127.0.0.1:7899  (gost 纯转发守护，本地端口永不消失)
   ├─ 节点 A  127.0.0.1:7896  ← SSH -D (连接服务器 443 端口)
   ├─ 节点 B  127.0.0.1:7895  ← SSH -D (连接服务器 443 端口)
   └─ 节点 C  127.0.0.1:7894  ← SSH -D (连接服务器 443 端口)
```

通过把三条节点写在 gost 的同一跳参数中（`-F "socks5://A,B,C?retries=3"`），自动实现高可用负载与故障转移。

**改造后实测**：三个上游各自稳定在 1.0 秒左右，前置入口延迟降至 **0.93 ~ 1.24 秒**（彻底告别 26 秒的地狱折磨），终端输出如行云流水般丝滑！
